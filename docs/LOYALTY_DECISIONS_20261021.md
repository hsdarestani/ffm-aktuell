# Visit proof and loyalty decisions

The implemented proof is **business confirmation of a physical visit**. It is not GPS tracking, an independently proven purchase, an automatically verified visit, a global point balance or a premium point multiplier.

Default program: five confirmed visits, at least 24 hours apart, for a real business-supplied reward with an HTTPS conditions link. The business can propose 2–50 visits and 1–168 hours between visits. Marketing moderation approves the program before it can issue new cards. No reward is invented or seeded. Editing a program submits it for review again. Existing cards preserve their target, minimum interval, benefit and conditions; amended rules apply to subsequent cycles. Existing cards can continue under their agreed terms while new programs are paused/reviewed.

The user requests a private 96-bit random code at a published approved branch; only its SHA256 hash is stored. The code expires after ten minutes, and no more than five requests per account per hour are accepted. An authorized owner or branch-scoped active staff editor confirms the actual visit. Own-business staff/owners cannot create self-visit claims. Both minting and confirmation enforce the interval. Customer row locks serialize distinct codes, preventing simultaneous codes from bypassing the interval.

Each confirmed visit can be allocated to exactly one card. A reached card receives a separate private reward code; staff confirms the reward only when it is actually handed over. Card and customer locks prevent parallel or replayed redemption. Additional confirmed visits remain in the ledger and can be allocated to the next eligible cycle. No public customer list or visit history exists. Private cards, codes and visits cascade on account deletion and are included in account export. Reviews can display a specifically labeled merchant-confirmed visit badge backed by a real visit record.

Repository PostgreSQL tests exercise authentication, ownership, scope, code hashing/expiry/single use, interval enforcement, immutable card terms, cycle allocation, private reads and deletion. Real PostgreSQL HTTP CI additionally races distinct visit/reward codes to test the transaction locks. No live customer, reward or visit is created in production for these tests. Operators must still supply actual rewards and contractual conditions and train staff to confirm only actual visits.
